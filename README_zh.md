# KB-Article-Sync: 双库企业级知识库同步网关与切分治理引擎

[English](README.md) | [中文](README_zh.md)

一套解耦、生产就绪的知识库同步网关微服务，用于将企业业务系统（CMS、OA、内部知识库、工单系统）的文章与文档自动化推送至 **Dify 知识库（RAG）**。

在基础同步能力之上，本服务进一步扩展了**研发知识库与 QA 文档库的双库智能分流**、**基于本地大模型的常数级 $O(1)$ 文档形态分类器**、**纯文本/Markdown 文本流的两层切分规则动态治理**，以及**针对界面删除（404 兜底）与跨库迁移的自愈式状态机**。

---

## 核心架构与业务价值

在企业级 RAG 生产落地过程中，知识入库面临以下关键工程挑战：
1. **异构文档形态分流**：通篇叙述性的研发规范、技术设计与结构化的问答对、FAQ 手册，对切分粒度与检索拓扑的要求截然不同，无法共用单一知识库策略；
2. **文本切分碎块化与语义断裂**：纯文本（`.txt`）与无格式 Markdown 往往含有大量不规则空行，若套用默认的 `\n\n` 父子切分规则，会将父块切得七零八落，破坏上下文连贯性；
3. **分段分隔符丢弃不变性**：Dify 的 `FixedRecursiveCharacterTextSplitter` 在按固定分隔符硬切时**会主动丢弃分隔符本身**。若直接使用 `\n\nQ:` 作为切分标记，会导致除首块外所有子块的 `Q:` 前缀被无情吃掉，严重破坏问答对完整性；
4. **检索后鉴权（RBAC）与出处回链**：检索召回后必须依据企业文章编号（`article_id`）做权限过滤，答案生成后需提供可点击的原文链接（`source_url`）；
5. **状态自愈与解耦运维**：当用户在 Dify 界面手工删除了某文档，或上次索引失败（400 / 404）时，同步网关必须具备无感自愈与重建能力。

`kb-article-sync` 独立部署，与 Dify 仅通过标准 HTTP Service API 交互，双方生命周期完全解耦。

## 核心技术特性

### 1. 研发知识库与 QA 文档库双库智能分流
- **研发知识库（`DATASET_RD`, `doc_type=1`）**：存放规范、架构说明、业务流程等连续文本，采用父子大上下文机制；
- **QA 文档库（`DATASET_QA`, `doc_type=2`）**：专收问答对、故障手册与 FAQ，采用精细化一问一答切分，保障相似度召回的极高命中率。

### 2. 常数级 $O(1)$ AI 文档分类器
- **微量正文流式抽取**：只读取文档头部（前 3,000 字，PDF 最多前 3 页），在内存中直接解析（`.docx` 通过解压缩直接读取 `word/document.xml`，PDF 使用轻量流式提取，纯文本/HTML 快速剥标签）；
- **耗时与文件大小无关**：无论文档是 100 MB 还是 5 KB，正文抽取与大模型判定耗时均恒定在秒级；
- **全链路 Fail-Open 容灾**：本地模型（如 DeepSeek-R1-14B）超时、宕机或无法识别时，自动回退到默认的研发知识库，**绝不阻断入库流**；
- **显式传参强制覆盖**：调用方可在推送时直接附带 `doc_type` 参数，跳过模型判定，方便人工干预与回溯。

### 3. 纯文本与 Markdown 两层切分规则治理
针对 Dify 库级分隔符无法兼顾二进制富文档与纯文本流的痛点，同步网关引入请求级 `process_rule` 动态下发：

```
[待入库文件]
     |
     v
[第一层：扩展名过滤]
     |-- 二进制/富格式 (.pdf, .docx, .pptx, .xlsx) -------> 维持 Dify 库级默认解析规则
     |
     v 文本流 (.txt, .md, .markdown, .mdx)
[第二层：正文形态判定 (扫描前 2 万字)]
     |
     |-- 1. "qa" 问答形态：包含 Q:/问: 开头的行 >= 5 且占非空行 >= 15%
     |      => 在每个问答对前自动埋入 @@QA@@ 占位符
     |      => 下发切分参数：父块 1024 / 子块 1024，均以 @@QA@@ 为切分符
     |      => 解决 Dify 丢弃分隔符缺陷：完整保留每段开头的 "Q:" 前缀！
     |
     |-- 2. "prose" 连续叙述形态：多句末标点，含硬换行折断或多级标题
     |      => 文本规范化：自动缝合非标点结尾的硬换行碎行，标题独立成段，段间统一 \n\n
     |      => 下发切分参数：父块 1024 / 子块 300，以 @@CHUNK@@ 为切分符
     |
     +-- 3. "list" 清单列表形态：目录流水、纯参数导出
            => 维持库级默认切分规则
```

> **架构深度复盘**：关于分隔符丢弃机理、切分碎块测试用例及存量治理指标，详见深度解析文档：[`docs/2026-10-30-dify-chunking-two-layer-rules.md`](./docs/2026-10-30-dify-chunking-two-layer-rules.md)。

### 4. 扩展的自愈式更新状态机
- **400 `Document is not available` 容错**：当 Dify 因文档处于索引中、上次失败或禁用而拒绝原地更新时，自动降级为“删除旧文档并原子重建”；
- **404 `Document not found` 自愈**：当运维在 Dify Web 界面手工删除了文档，但本地 `mapping.db` 仍记录旧 ID 时，接口命中 404 自动转为新建流程，并将新 `document_id` 同步写入数据库，返回 `status="created"`；
- **跨库自动迁移**：若文章修改了 `doc_type`（例如由普通文档改判为 QA 文档），服务会自动在原库中下线旧记录，并在新库中重建，彻底杜绝多库重复数据；
- **全量同步零错误安全闸（`full_sync: true`）**：只有当当前批次错误数为 0 时，才会执行未在批次中的历史在线文档下线，防止脏数据引发误清库。

## 快速配置与部署

### 1. 配置环境变量
复制配置模板至 `env.sh`：

```bash
cp env.example.sh env.sh
chmod 600 env.sh
vi env.sh
```

```bash
# ----------------- Dify 核心配置 -----------------
DIFY_API_KEY=dataset-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
KB_SYNC_TOKEN=change-me-to-a-long-random-string
DIFY_BASE=http://127.0.0.1:8082/v1
PORT=8090

# 双知识库 ID
DIFY_DATASET_ID=3e5855a3-f2a5-4b96-a05d-eff18406f66a       # 研发知识库 (doc_type=1)
DIFY_DATASET_QA_ID=d5582337-85ed-43a3-abc2-aa9b1c24913b    # QA 文档库 (doc_type=2)

# ----------------- 本地大模型分类器 -----------------
CLASSIFIER_BASE=http://127.0.0.1:8001/v1
CLASSIFIER_MODEL=deepseek-r1-14b-awq
CLASSIFIER_TIMEOUT=90
CLASSIFIER_CHARS=3000
CLASSIFIER_PDF_PAGES=3

# ----------------- 元数据配置 -----------------
META_FIELDS=source_url,article_id
MAPPING_DB=./mapping.db
```

### 2. 进程管理与验证
```bash
./tmux.sh start      # 启动后台常驻服务并校验 /healthz
./tmux.sh status     # 查看进程健康状态
./tmux.sh logs       # 滚动查看日志（Ctrl+C 仅退出查看，不影响服务）
./tmux.sh restart    # 重载配置并重启
./tmux.sh stop       # 安全停止后台服务

# 运行自动化集成测试
./selftest.sh
```

## 接口规范

所有请求均需在 Header 中附带鉴权令牌：
```http
X-KB-Sync-Token: <KB_SYNC_TOKEN>
```

### 1. 批量文章推送
- **路由**：`POST /sync/kb/article/push`
- **Content-Type**：`application/json`
- **单批上限**：200 条

#### 请求体示例
```json
{
  "full_sync": false,
  "items": [
    {
      "article_id": 1001,
      "title": "研发架构规范与最佳实践",
      "file_name": "engineering_standards.docx",
      "file_url": "https://cms.internal.example.com/files/1001.docx",
      "source_url": "https://cms.internal.example.com/article/1001",
      "publish_status": "published",
      "updated_at": "2026-10-30T10:00:00+08:00",
      "category": "技术规范",
      "author": "架构委员会",
      "secret_level": "内部",
      "doc_type": 1
    }
  ]
}
```

> **提示**：`doc_type` 为可选字段（`1` 为研发知识库，`2` 为 QA 文档库）。若未提供，服务将自动提取前 3,000 字交由大模型快速判定。

#### 响应结果（`200 OK`）
```json
{
  "code": 200,
  "status": "success",
  "msg": "Batch processing completed",
  "data": {
    "accepted": 1,
    "rejected": 0,
    "offline": 0,
    "errors": []
  }
}
```

### 2. 单条直接文件推送
- **路由**：`POST /api/sync_article`
- **Content-Type**：`multipart/form-data`

```bash
curl -F "article_id=1001" \
     -F "title=Z5 参数及常见问题" \
     -F "source_url=https://cms.internal.example.com/article/1001" \
     -F "publish_status=published" \
     -F "doc_type=2" \
     -F "file=@/path/to/faq.txt" \
     -H "X-KB-Sync-Token: $KB_SYNC_TOKEN" \
     http://127.0.0.1:8090/api/sync_article
```

## 安全建议

- **权限防护**：确保 `env.sh` 的权限为 `600`，杜绝多用户环境下的密钥泄露；
- **高熵令牌**：`KB_SYNC_TOKEN` 务必采用高强度随机字符串（如 `openssl rand -hex 32`）；
- **数据留存与灾备**：定期对 `mapping.db` 进行备份，确保文章编号与知识库文档映射关系持久化。
