# Dify 父子分块治理与 kb-sync 两层切分规则改造

> 记录日期：2026-10-30
> 适用范围：kb-article-sync（知识库文章同步网关）+ Dify 研发知识库 / QA 文档库

## 1. 问题背景

研发知识库使用 `hierarchical_model` 父子分块：父块按 `\n\n` 切、最大 1024 tokens，子块按 `\n` 切、最大 200 tokens。

- pptx / pdf / docx 这类由 Dify 自己解析的文档，分块效果正常，检索没问题。
- 真正出问题的是**纯文本（txt）**：原文排版里大量空行，`\n\n` 把**父块**切得七零八落，父块之间语义断裂，连基础检索都失效。
- 但不能直接改库级分隔符：全局放宽后，子块会变长，命中精度下降。

结论：**不动库级规则，改为文档级 `process_rule`**——在上传那一刻按文档实际形态选择切分参数。

## 2. 摸清的 Dify 机制（改造前提）

| 点 | 结论 |
| --- | --- |
| 选哪个分段器 | 看顶层 `doc_form`（`text_model` / `hierarchical_model` / `qa_model`），不是 `process_rule.mode`；不传会兜底成 `chunk_structure or "text_model"`，父子参数全部作废 |
| 固定分隔符行为 | `FixedRecursiveCharacterTextSplitter` 先按 `fixed_separator` 硬切，**分隔符本身被丢弃**（不是 keep_separator），只有超长段才走递归（`\n\n` → `\n` → `。` → 空格） |
| 规则存储 | 库级默认在 `dataset_process_rules`，文档通过 `dataset_process_rule_id` 绑定；请求不带 `process_rule` 时用 `dataset.get_latest_process_rule()` |
| 文档级规则 | `create-by-file` / `update-by-file` 显式带 `process_rule` 时，库级默认不参与 |
| 原地更新限制 | 只有 `display_status == available`（索引完成 + 未归档 + 已启用）才能更新，否则 400 `not available` |
| 文档被手工删除 | 更新接口回 404，需要按新建处理 |

## 3. 方案：两层规则判定

在同步服务上传前做两层判断，只影响文本流，其它格式行为完全不变。

### 第一层：扩展名

只有 `.txt / .md / .markdown / .mdx` 进入内容形态判断；pdf / docx / pptx / xlsx 继续用原有父子规则，避免对 Dify 侧解析结果做无依据的猜测。

### 第二层：正文形态

| 形态 | 判定条件（只看前 2 万字） | 去向 | 切分规则 |
| --- | --- | --- | --- |
| `qa` | `Q:` / `问：` 开头行 ≥ 5 且占非空行 ≥ 15% | QA 文档库 | 父/子都用标记 `@@QA@@` 切，1024 / 1024，一个问答对 = 一父块 = 一子块 |
| `prose` | 句末行 ≥ 2，且（标题行 ≥ 3 或平均行长 ≥ 40 或硬换行比例 ≥ 0.35） | 研发知识库 | 先合并硬换行、标题独立成段，再按占位符 `@@CHUNK@@` 切，1024 / 300 |
| `list` | 其余（目录、参数流水、表格导出） | 研发知识库 | 沿用库级默认父子规则 |

### 两个关键实现细节

1. **分隔符用正文里不存在的标记，而不是 `\n\nQ:`**
   分隔符在切分时会被丢弃，用 `\n\nQ:` 会把每段的 `Q:` 一起吃掉（实测第 2 块起开头变成 “ T100 最多…”）。
   改为在每个问答对前插入 `@@QA@@`，切完丢弃标记本身，父块仍以 `Q:` 开头。

2. **叙述稿先规范化再上传**
   合并被硬换行折断的句子（不以句末标点结尾的行接回上一行），标题行独立成段，段间统一 `\n\n`；正文里不含占位符，切分器找不到分隔符时才会退化成按 `max_tokens` 的递归合并，等价于“只在语义边界处切”。

## 4. 验证结果

### QA 文本（8 个问答对）

| 版本 | 父块 | 子块 | 以 `Q:` 开头的子块 | < 30 字碎块 |
| --- | --- | --- | --- | --- |
| 改前（`\n\nQ:`） | 8 | 8 | 1/8 | 0 |
| 改后（`@@QA@@`） | 8 | 8 | 8/8 | 0 |

### 叙述文本（8 行硬换行 + 4 个标题）

合并后 1 个父块 / 1 个子块，176 字；标题“1. 概述”“2. 字段要求”独立成段，不再按行碎裂。

### QA 文档库存量文档（Z5 参数及常见问题）

子分块规则改为 `@@QA@@` 后重新处理：子块 79 → 29，1 父块 = 1 子块，< 30 字块 0，检索探针 score ≈ 0.999。

## 5. 兼容性与兜底

- **其它格式不受影响**：pdf / docx / pptx / xlsx 仍走原来的父子规则。
- **QA 库的普通文档**：`doc_type=2` 但不是问答形态时仍不下发 `process_rule`，沿用库级设置。
- **400 `not available`**：既有逻辑，删除后重建，保证推送一定落地。
- **404 `Document not found`**：新增兜底——文档在 Dify 界面被手工删除但映射表还留着旧 id 时，直接改走新建，并把新 `document_id` 回写映射表；返回结果的 `result` 也改为按实际 `document_id` 判断（`created` / `updated`），避免兜底重建被误报成更新。

## 6. 运维与回滚

- 服务用 tmux 常驻，`./stop.sh` / `./start.sh` 启停，日志 `logs/app.log`，映射表 `mapping.db`（SQLite，表 `kb_document_mapping`）。
- 发布前做 `ast.parse` 语法检查，替换文件后重启并看 `/healthz`。
- 每次改造都留了备份（`post.py.bak-*`），回滚直接换回旧文件重启即可。
- 上线前自测用的测试文章（990001 / 990002 / 990003）已从 Dify 与映射表清理，不影响线上检索。

## 7. 后续可选

- 存量 txt 文档逐步重推，统一走新的形态判定（重推即重建文档）。
- 评估 pptx / Excel 是否需要独立规则（当前维持库级默认）。
- 若文档在 Dify 界面被删，映射表会留下陈旧记录：现在能自愈（404 兜底），但可考虑定期对账清理。
